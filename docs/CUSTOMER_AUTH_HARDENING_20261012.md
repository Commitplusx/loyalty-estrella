## Contrato preparado

- Dos tablas privadas: `loyalty_customer_accounts` enlaza cliente con Auth, alias de correo aleatorio privado y teléfono verificado; `loyalty_login_challenges` separa prueba de acceso de OTP de pedido. Un OTP de login no crea pedidos ni autoriza checkout.
- Reclamo de envío idempotente por teléfono/clave, pending/sent/failed/verified/used, hash por desafío, cinco minutos y cinco intentos. Una respuesta perdida reutiliza el desafío aceptado; una petición concurrente no vuelve a enviarlo.
- Sólo se inicia acceso de una ficha registrada con términos aceptados. El alias se genera en el servidor y nunca en la web. No es el correo de contacto ni el correo canónico del aliado/repartidor; no modifica sus cuentas.
- Una prueba válida crea/reutiliza un intento de identidad duradero. Supabase Auth crea la cuenta customer con contraseña aleatoria no distribuida, email confirmado y app_metadata de servidor `account_kind=loyalty_customer`. La vinculación SQL comprueba ID/correo/metadata inmutable/confirmación. Un token o dato editable del navegador no la autoriza.
- Después de vincular, Admin generateLink emite una credencial de acceso de un uso; el cliente la intercambia con Auth verifyOtp (type email) para obtener la sesión estándar. No se fabrican JWT ni se guarda una bandera de autorización en sessionStorage.
- Crear una cuenta a medias o perder la respuesta se recupera con el mismo alias y prueba vigentes, con límites. No busca todos los usuarios ni cambia contraseñas de cuentas existentes. Transferir el teléfono invalida la identidad anterior y genera otra, evitando reactivar al dueño previo.
- Ratelimit persistido existente: envío por IP/por teléfono y verificaciones por IP/teléfono; namespaces separados de checkout. Errores explícitos, plazo de ocho segundos y cuerpos/respuestas acotados pendientes de completar.

La suite SQL `customer-login-identity.sql` pasó con ROLLBACK: consentimiento, reclamo de envío, reutilización, códigos no enviados, teléfono equivocado, intento erróneo duradero, identidad única, vinculación Auth, replay, transferencia de teléfono, metadata editable falsa, expiración y acceso sólo servidor. Los fixtures de Auth tienen únicamente las columnas requeridas verificadas; auth.users no tiene triggers de usuario. No se envían correos/WhatsApps.

Pruebas locales adicionales aprobadas: quince del dominio de acceso (envío/estado persistido, duplicados, fallos de proveedor/Auth/DB y recuperación), nueve del adaptador usando el SDK real con transporte ficticio completo, cinco de JSON acotado y diecisiete regresiones de autorización de avisos. `http-request.ts` comparte límite/plazo/cancelación; auth-otp tiene lectura máxima de 256 KiB/cinco segundos y POST explícito.
